# Обновления и восстановление
Автор: Arahort — arahort.pro, alex@arahort.pro.
## Проверка и установка
В админке сначала проверь выпуски, затем подтверди выбранную версию. Сведения хранятся не больше часа; при устаревшем результате повтори проверку. Обновлятор принимает только стабильные `vX.Y.Z` Releases указанного публичного GitHub-репозитория, проверяет совпадение версии, ожидаемое имя GHCR и `sha256` образа. HTTPS GitHub является границей доверия первого выпуска; отдельной авторской подписи manifest пока нет.
```sh
sudo dndctl check
sudo dndctl update
sudo dndctl status
```
Эти команды запускаются по отдельности. Обновлятор не меняет PostgreSQL major version, Compose, самого себя или конфигурацию обратного прокси через кнопку. `minimumUpdaterVersion` и `schemaVersion` несовместимого выпуска блокируют такое обновление. Выпуск с новым форматом требует отдельного описанного автором обслуживания. Хостовые файлы первого выпуска обновляй только из проверенного архива после резервной копии; `.env` и постоянные папки сохраняются.
## Последовательность
1. Скачивание закреплённого digest нового образа до остановки игры.
2. Режим обслуживания: блокировка новых изменений, ожидание запущенных HTTP/Socket.IO и AI-заданий до 20 минут.
3. Остановка приложения, `pg_dump -Fc`, архив файлов и Google-профиля, копия `.env`, SHA-256 резервной копии.
4. Запуск нового образа с закрытой записью. Приложение применяет совместимую схему, затем проходит HTTP health-проверку.
5. Открытие записи при успехе. При ошибке до открытия записи — остановка нового приложения, возврат полной копии БД/файлов и прежнего образа, повторная проверка.
После попытки открыть запись новые изменения уже могли поступить даже при потере ответа служебного запроса. В таком случае старую БД автоматически не восстанавливаем: сохраняем данные новой версии, по возможности закрываем запись снова и выставляем `recoveryRequired`. Проверь версию и целостность данных, затем используй `sudo dndctl recover`. Так сбой подтверждения не стирает уже принятые ходы.
Даже при заявленной совместимости отката копия восстанавливается: частично выполненная миграция может менять данные. Старые образы автоматически не удаляются, чтобы не потерять возможность возврата. На диске нужно место для новой версии и полной копии данных; резервные копии не заменяются автоматически.
Если питание или служба пропали посередине, обновлятор помечает `recoveryRequired`. Автоматически открывать запись в таком состоянии нельзя: сначала проверь образ, журналы и резервную копию. Состояние записывается атомарно в отдельный root-owned файл `/var/lib/dnd-ai-arahort/control/maintenance.json`, который смонтирован приложению только для чтения как `/run/dnd-control/maintenance.json`. При запуске приложение читает его вместо неизменяемого env контейнера; отсутствующий или неправильный файл закрывает запись. В начале drain и при восстановлении значение `true`, после успешного открытия — `false`, поэтому обычный restart/reboot сохраняет верное состояние. Контрольный файл не берётся из резервной копии и не требует пересоздания контейнера.
## Резервные копии
```sh
sudo dndctl backup
```
Копия создаётся в `/var/lib/dnd-ai-arahort/backups/<UTC timestamp>/`. В ней есть `database.dump`, `files.tar.gz`, `installation.env`, `backup.json`; `INCOMPLETE` помечает неудачную попытку. Копии содержат Google-токены, сессии, приватные партии и пароль БД. Доступ — только root; храни внешнюю копию в защищённом месте. Архив не предназначен для загрузки в публичные Issues.
Полное восстановление заменяет все более поздние данные. Останови обычную работу и укажи точную папку:
```sh
sudo dndctl restore /var/lib/dnd-ai-arahort/backups/UTC_TIMESTAMP --confirm-restore
```
Восстановление проверяет состав и контрольные суммы копии. Не подменяй файлы внутри резервной папки. Если автоматический откат не удался, запись остаётся закрытой; изучи `sudo dndctl status`, `sudo journalctl -u dnd-ai-arahort-updater --no-pager -n 100` и журналы приложения. После ручного восстановления и проверки образа/БД открыть запись можно `sudo dndctl recover`.
Сброс администраторского пароля:
```sh
sudo dndctl reset-password ADMIN_LOGIN
```
Пароль запрашивается скрыто и передаётся через stdin, а не аргументы процесса.
## Локальное тестирование нового билда
На тестовом сервере подготовь новый скомпилированный `app/` и собери образ с другим тегом:
```sh
sudo docker build -t dnd-ai-arahort:test-next /opt/dnd-ai-arahort
sudo dndctl update-local dnd-ai-arahort:test-next
```
Это две отдельные команды. Локальная установка проходит тот же drain, backup, restart и rollback. В конфигурацию сохраняется неизменяемый ID образа. Тег не передаётся через админку: локальное обновление доступно только root по SSH. Не очищай прежние образы до проверки обновления и копии.
## Узкий протокол обновлятора
Сокет `/run/dnd-ai-arahort/updater.sock` принадлежит `root:dnd-updater`, права `0660`; директория `0750`. Контейнер приложения получает только эту директорию и дополнительную группу. Docker socket в него не монтируется.
- `GET /v1/status` — состояние, версия и digest.
- `POST /v1/check` с `{}` — проверка доверенного репозитория.
- `POST /v1/apply` с `{"version":"0.1.1"}` — установка только свежепроверенной выбранной версии.
Запросы приложения к сокету должны проходить серверную проверку администраторской сессии. Никаких произвольных путей, proxy-параметров, команд и URL этот протокол не принимает.
